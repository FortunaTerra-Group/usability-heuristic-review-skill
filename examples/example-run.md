A worked example of this skill's output, on a single-file toy surface: a fictional SaaS usage
dashboard called Contoso Cloud. The page shows three cards (API usage, Team, Billing) and a
Recent Activity table. It has no backend and no persona documentation; both of those absences
are load-bearing for this walkthrough, not incidental.

**Persona source.** This toy has no product or persona documentation, because it was invented
for this example rather than pulled from a real backlog. Per the skill's own instruction never
to invent a persona, that absence is finding 0 below, and every downstream judgment about what a
user needs is flagged as an assumption resting on a generic "engineering lead checking their
account" reader.

## Executive read (top 5 by severity)

0. **[0 · Help and documentation] Whole surface.** No documented target user. Every persona
   judgment below is an assumption; the artifact should say who this dashboard is for.
1. **[3 · Visibility of system status] API Usage card.** The "Updated 2 minutes ago" badge is
   static markup (`<span class="last-updated">Updated 2 minutes ago</span>`) with no timestamp
   attribute or fetch time behind it. It will read the same two minutes whether the page was
   rendered seconds ago or has been sitting cached for a week, asserting a freshness the system
   has no way to verify. Severity 3 because a capacity-planning decision made on data assumed
   fresh, when it structurally cannot be, produces a wrong answer instead of a merely
   stale-looking one.
2. **[2 · Match to the real world] API Usage card.** The usage figure reads a bare
   "14,382 / 20,000" with no unit anywhere on the card, not calls, not requests, not gigabytes.
   A reader cannot tell what is being counted without guessing.
3. **[2 · Consistency and standards] Team card vs. Billing card.** The Team card calls the count
   "Seats" ("8 of 10 used"); the Billing card calls the identical number "Licenses in use" (8).
   A reader comparing the two cards has to work out that they mean the same thing.
4. **[2 · Aesthetic and minimalist design] API Usage card, reset-date caption.** The "Usage
   resets on the 1st of each month" caption renders at roughly 2.3:1 contrast (`#aaaaaa` on
   white), under the WCAG AA minimum of 4.5:1 for normal text and under the 3:1 minimum for
   large text too. It is legible to some readers and not to others.
5. **[2 · User control and freedom] Whole surface.** Every link and button has its focus
   outline removed (`a:focus, button:focus, input:focus { outline: none; }`) with no replacement
   style defined anywhere in the stylesheet. A keyboard-only user tabbing through the page has
   no way to see which control is about to activate.

## Quick-win vs. structural split

**Quick wins** (copy, label, or CSS changes, no new data flow):
- Add a unit noun to the usage figure, for example "14,382 / 20,000 requests" (finding 2).
- Use one word for the seat count on both the Team and Billing cards (finding 3).
- Raise the caption color to a shade that clears 4.5:1 against white (finding 4).
- Add a visible focus style, for example a box shadow or outline color, to replace the one
  removed globally (finding 5).
- Render a "No recent activity yet" row when the activity table has zero entries (finding 6).

**Structural** (need a data or state change):
- Replace the static "Updated 2 minutes ago" text with a real "as of" timestamp wired to the
  actual render or fetch time (finding 1). This is the severity-3 item, and it needs the page to
  actually carry a timestamp value, not just different copy.
- A written target user for the surface (finding 0).

## Handoff pointers

- Finding 1 (fake freshness badge): engineering, contingent on the data layer actually exposing
  a render or fetch timestamp to build a real "as of" marker from.
- Findings 2, 3, 4, 5, and 6: a one-sprint engineering fix, no design review needed.
- Finding 0: product, before the next audit of this surface.
